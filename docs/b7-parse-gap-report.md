# B7 文本解析缺口报告（成员 C 人工验收发现）

> 2026-11-01，C8 人工验收（微信开发者工具）中成员 C 实测发现三个解析问题。
> 本报告按任务书要求提供请求、预期与实际结果；修复提案见分支
> `feat/backend-b7-parse-extension`（原 B7 测试全部保持通过，后端全量 322 项通过）。

参考时刻统一为 `2026-11-01T12:00:00+08:00`，时区 `Asia/Shanghai`。

## 问题一：逗号分隔的「同一事项 + 截止说明」被拆坏

**请求**：`明天下午3点提醒我交实验报告，下周五前交报告`

- 预期：一张草稿——标题「交实验报告」，提醒 11-02 15:00，截止 11-06。
- 实际：一张草稿，标题为整句原文，`needs_confirmation=['date','remind_at']`（日期不明、提醒时刻不明）。两个日期词（明天/下周五）导致日期解析放弃，标题也未清理。
- 原因：原实现只处理「恰好一个日期词 + 恰好一个时刻」的子句；逗号既不是分隔符，多日期词也没有归并规则。

**同源问题**：`明天下午3点提醒我交实验报告，4点截止`

- 预期：一张草稿——提醒 11-02 15:00，截止 11-02（due_at 只有日期粒度，4 点不入库）。
- 实际：`needs_confirmation=['remind_at']`（提醒时刻不明）。两个时刻（下午3点、4点）导致提醒时刻放弃，但「下午3点」本身是明确的。

## 问题二：省略「下午」的中文时刻一律判「须确认」（契约决策，待 B 拍板）

**请求**：`明天三点提醒我交作业`（用户认为很容易理解）

- 预期（用户视角）：提醒 明天 15:00。
- 实际：`needs_confirmation=['remind_at']`。
- 现状是 B7 契约的有意设计（「省略上午/下午的中文“三点”须确认」）。本报告提出两种选项供 B 决策：
  - 保持谨慎（现状）：歧义时刻标待确认，用户在草稿里确认；
  - 默认下午：对 1-6 点的裸时刻默认下午（12 点默认中午），并保留「凌晨/早上/上午」显式覆盖。
- 修复提案分支**未**改动此行为；仅在「晚间语境」（今晚/明晚等日期词）下把裸时刻按晚上解释（今晚六点→18:00），因为该语境不歧义。

## 问题三：不支持「N分钟/N小时后」相对时间

**请求**：`今晚六点吃饭，吃完饭15分钟后提醒我吃药`

- 预期：两张草稿——「吃饭」（今晚 18:00，未说提醒，标「仅有时刻，未说明要提醒」）；「吃药」提醒 今天 18:15。
- 实际：一张草稿，整句原文作标题，`needs_confirmation=['date','remind_at']`。「今晚」不是日期词，「15分钟后」无规则。

**同源问题**：`30分钟后提醒我交作业` → 实际 `['date','remind_at']`，预期提醒 12:30。

## 修复提案（feat/backend-b7-parse-extension）

1. 逗号子句拆分规则：无时间表达的子句并入前句；带截止标记且无「提醒」的子句并入前句（同一事项）；其余视为独立事项。
2. 多日期词：第一个作提醒日期，出现截止标记时最后一个作截止日期；多时刻取第一个明确时刻（带时段/带分钟/24 小时制）。
3. 新增「今晚/明晚/昨晚/后天晚」日期词；晚间语境裸时刻按晚上解释。
4. 新增「N分钟后/N小时后/半小时后」相对时间：锚点为本句明确时刻 → 前文最后一个时刻 → 参考时刻；相对时刻自带日期，不再标日期不明。
5. 修复连接词正则 `吃完?饭` 会吞掉标题「吃饭」的缺陷（空标题回退原文）。
